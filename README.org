#+title: Codex sandbox

My personal development environment for Codex CLI, powered by rootless
Podman.

It serves three roles:

1. *Workspace management*: expose only selected working directories
   from the host system to Codex. The rest of the host filesystem is
   not mounted at all.

2. *Codex customization*: set system-wide permission defaults and
   provide global ~AGENTS.md~ instructions and personal skills.

3. *Controlled environment*: provide selected development tools and
   toolchains, independently of those installed on the host.

Both the container boundary and Codex's own Linux sandbox remain
enabled.

This README is also available [[file:docs/codex-sandbox.pdf][as a PDF]].

* Requirements

On the host system:

- Rootless Podman.

- Bash and standard GNU command-line tools.

- Unprivileged user namespaces.

- Python 3 and PyYAML if you use a workspace configuration or run ~just check~.
  On Debian-based systems, install ~python3-yaml~.

- ~just~ if you want to use the repository [[https://github.com/casey/just][Just]] recipes.

- ShellCheck on the host if you want to run ~just check~.

Tools used inside the sandbox are installed in the image; host
installations are not exposed to the container.

* Usage

~codex-sandbox~'s launcher is the ~run.bash~ Bash script. To run it by
name, create a symlink in a directory on the host's ~PATH~.

#+begin_src bash
  ln --symbolic /path/to/codex-sandbox/run.bash ~/bin/codex-sandbox
#+end_src

All commands below will assume ~codex-sandbox~ is available.

** Workspace

Before running ~codex-sandbox~ commands, it is important to understand
the /workspace/.

The workspace brings selected host directories together beneath
~/workspace~ inside the container. The directories remain in their
original host locations; changes inside their mounts persist on the
host. In contrast, files created directly under ~/workspace~ disappear
when the container exits.

The optional configuration file at
~$HOME/.config/codex-sandbox/config.yaml~ defines the workspace by
assigning each directory a name under ~workspace~:

#+begin_src yaml
  workspace:
    codex-sandbox: ~/src/codex-sandbox
    project-1: ~/src/project-1
    project-2: ~/src/project-2
#+end_src

This describes the following directory layout inside the container:

#+begin_example
  /workspace/
  ├── codex-sandbox/  (mounted from ~/src/codex-sandbox)
  ├── project-1/      (mounted from ~/src/project-1)
  └── project-2/      (mounted from ~/src/project-2)
#+end_example

Names must start with a letter or digit and contain only letters,
digits, dots, underscores, or hyphens. The ~workspace~ mapping must
contain at least one directory, and each host directory must have one
name. Paths may be absolute, start with ~~/~, or be relative to the
configuration file's directory.

If ~$XDG_CONFIG_HOME~ is set, the default file is
~$XDG_CONFIG_HOME/codex-sandbox/config.yaml~. The
~CODEX_SANDBOX_CONFIG~ environment variable selects another file.

*Important*: if you resume a previous Codex session, you remain
responsible for mounting the right projects in the workspace!

** Launching Codex

The launcher prepares the container and its mounts, then runs the
regular Codex CLI with ~--no-daemon~. Exiting Codex ends the
container.

*** Empty workspace
:PROPERTIES:
:CREATED:  [2026-11-14 Sat 14:48]
:END:

The simplest use case is to use ~--empty-workspace~ or ~-e~ to ignore
the workspace projects and start directly in ~/workspace~, with no
host projects mounted:

#+begin_src bash
  # On the host (either form):
  codex-sandbox --empty-workspace
  codex-sandbox -e

  # Equivalent Codex command inside the container:
  codex -C /workspace
#+end_src

This is useful for brainstorming or asking quick questions. Files
created under ~/workspace~ disappear when the container exits, but
Codex login, conversation history, and other state in the private home
volume persist. Leaving Codex exits the container.

*** Working directories

You can pass directories explicitly to ~codex-sandbox~. An already
registered directory will automatically use its configured name
internally. An unregistered directory will simply use its basename and
will be registered for the duration of the session.

Pass a single working directory to start a new conversation directly
about this project:

#+begin_src bash
  # On the host
  codex-sandbox ~/src/project-1

  # Equivalent Codex command inside the container
  codex -C /workspace/[project-name]
#+end_src

When multiple directories are passed, the first is the starting
directory. Each additional directory is passed with ~--add-dir~, so
the conversation can edit those projects too:

#+begin_src bash
  # On the host
  codex-sandbox ~/src/project-1 ~/src/project-2

  # Equivalent Codex command inside the container
  codex -C /workspace/[project-name-1] --add-dir /workspace/[project-name-2]
#+end_src

When passing working directories, your registered projects stay
mounted normally. Only the project directories you pass are included
in the new conversation's writable scope.

*** Command Center

With a workspace configured, run ~codex-sandbox~ without any arguments
to open Codex's Command Center.

#+begin_src bash
  codex-sandbox
#+end_src

The Command Center opens in the first project listed in the workspace
configuration. Resume a saved conversation to use its saved directory.
If you have no conversations yet, press ~n~ to start one in the first
project. Pass a working directory to the launcher to start directly in
another project.

Without a configuration file, pass a working directory or use
~--empty-workspace~. An invalid file or an unavailable registered
directory stops a normal launch. ~--empty-workspace~ bypasses the
file.

** Codex arguments

Use ~--~ to pass arguments to Codex. Codex starts in the first
explicit directory or, when none is supplied, the first configured
project. All configured projects remain mounted.

#+begin_src bash
  codex-sandbox -- --model gpt-6.1-sol
  codex-sandbox ~/src/my-project -- --model gpt-6.1-sol
#+end_src

** Just recipes

The ~Justfile~ wraps the common repository workflows. Run ~just~ at
any time to list the available recipes.

|---------------------+----------------------------------------------------------------------------------|
| Recipe              | Action                                                                           |
|---------------------+----------------------------------------------------------------------------------|
| ~check~             | Run Bash syntax checks, ShellCheck, launcher stub checks, and ~git diff --check~ |
| ~configure-signing~ | Configure this clone to sign commits with the owner's GPG key                    |
| ~pdf~               | Render this README as a styled PDF through Pandoc and Typst                      |
| ~build~             | Build or refresh the image without launching Codex                               |
| ~run ARGS...~       | Forward arguments to ~run.bash~ and launch Codex                                 |
| ~containers~        | List running containers created from the sandbox image                           |
| ~shell [CONTAINER]~ | Open a login Bash shell in a running sandbox container                           |
|---------------------+----------------------------------------------------------------------------------|

For example:

#+begin_src bash
  just check                         # Run static validation
  just configure-signing             # Configure signed commits in this clone
  just pdf                           # Render docs/codex-sandbox.pdf
  just build                         # Build or refresh without launching
  just run                           # Open the Command Center
  just run -e                        # Launch without host workspace mounts
  just run ~/src/my-project          # Launch Codex
  just containers                    # List running sandbox containers
  just shell                         # Open Bash in the running container
#+end_src

Run ~just shell~ from another terminal while Codex is running. If
several sandbox containers are active, select one explicitly:

#+begin_src bash
  just shell CONTAINER_ID_OR_NAME
#+end_src

Arguments to ~just run~ are forwarded to ~run.bash~, including the
separator for Codex arguments:

#+begin_src bash
  just run ~/src/my-project -- --model gpt-6.1-sol
#+end_src

* Building the image
:PROPERTIES:
:CREATED:  [2026-11-14 Sat 15:02]
:END:

The image is built automatically if it does not exist. To build or
refresh it without starting Codex:

#+begin_src bash
  codex-sandbox --build
#+end_src

Rebuild to pick up changes to the image's tools, container scripts, or
home template.

The first launch after a build may be slower: with native OverlayFS,
Podman prepares the image's UID/GID mapping for ~--userns=keep-id~.
Subsequent launches reuse that preparation. See Podman's [[https://github.com/podman-container-tools/podman/blob/main/docs/tutorials/performance.md#choosing-a-storage-driver][performance
guide]].

The image is built from ~debian:trixie-slim~ and tagged
~codex-sandbox:local~. See the [[file:Containerfile][Containerfile]] for more details.

The resulting container root filesystem is read-only at
runtime. Writable locations are mounted explicitly by ~run.bash~.

Every build uses Podman's ~--pull=newer~ policy. This checks for a
newer ~debian:trixie-slim~ base so current Debian package updates are
incorporated when available. Node.js and the other explicitly pinned
tools are updated by changing their build arguments and checksums.

* Filesystem and persistence

|-------------------------------------+-----------------------------+-----------------------------|
| Location                            | Backing                     | Lifetime                    |
|-------------------------------------+-----------------------------+-----------------------------|
| Selected ~/workspace/NAME~ children | Optional host bind mounts   | Persists on the host        |
| ~/workspace~ root                   | 1 GiB private tmpfs         | Removed with the container  |
| ~/home/codex~                       | ~codex-sandbox-home~ volume | Persists across containers  |
| ~/tmp~                              | 1 GiB private tmpfs         | Removed with the container  |
| ~/run~                              | 64 MiB private tmpfs        | Removed with the container  |
| ~/dev/shm~                          | 1 GiB private shared memory | Removed with the container  |
| Container root                      | Read-only image             | Replaced with the container |
|-------------------------------------+-----------------------------+-----------------------------|

Files written directly to the root of the workspace (~/workspace~)
disappear when the container exits. Only changes inside selected child
directories persist on the host. In ~--empty-workspace~ mode, no host
working directory is mounted and every file created below ~/workspace~
is disposable.

** Custom home

The build installs ~image/usr/local/share/codex-sandbox/home/~ as
~/usr/local/share/codex-sandbox/home/~. At every container start, the
entrypoint overlays this template onto ~/home/codex~. Matching paths
are refreshed from the image; files absent from the repository
template are left untouched.

This separates two kinds of home data:

- Repository-managed configuration comes from the home template and changes
  through an image rebuild.

- Runtime state such as Codex credentials, sessions, user-installed
  tools, and downloaded toolchains remains in the persistent
  ~codex-sandbox-home~ volume.

Removing a path from the home template does not remove a copy already present in
the persistent volume. Deletion requires an explicit migration or
recreation of the volume.

** Removing persistent state

After every sandbox container has stopped, the persistent home can be
removed:

#+begin_src bash
  podman volume rm codex-sandbox-home
#+end_src

This permanently deletes Codex credentials and sessions, user-global
npm packages, uv-managed Python versions and tools, Go-installed
tools, Playwright browser binaries, cached Typst Universe packages,
SDKMAN and its installed JDKs, and Elan's downloaded Lean toolchains and
configuration. It does not
affect selected host working directories.

* Configuration

The image installs ~image/etc/codex/config.toml~ at
~/etc/codex/config.toml~ inside the container. This file selects the
~container-workspace~ permission profile by default. An explicit
~sandbox_mode~ setting or ~--sandbox~ argument takes precedence.
Rebuild the image to apply changes to the bundled configuration or rules.

The custom home hosts other global Codex instructions and skills:

#+begin_example
  image/usr/local/share/codex-sandbox/home/
  ├── .agents/
  │   └── skills/
  │       ├── build-silverbullet-wiki/
  │       │   ├── SKILL.md
  │       │   ├── agents/openai.yaml
  │       │   └── assets/repeater-style.md
  │       └── publish-project-pdf/
  │           ├── SKILL.md
  │           ├── agents/openai.yaml
  │           ├── assets/theme.typ
  │           └── references/visual-review.md
  └── .codex/
      └── AGENTS.md
#+end_example

This makes ~codex-sandbox~ not only a development environment, but
also a convenient Git-backed set of instructions for Codex.

The template's ~.codex/AGENTS.md~ explains the workspace layout and
installed tools to every Codex session and routes PDF requests to the
corresponding skill. Project-level ~AGENTS.md~ files remain scoped to
their own selected directories and take precedence where they apply.

** Container timezone

To set local time inside the container, add the optional ~timezone~
key at the top level of the launcher's ~config.yaml~.

#+begin_src yaml
  timezone: Europe/Paris
#+end_src

Use an IANA timezone name. The launcher validates it against the
host's timezone database, provided by ~tzdata~ on Debian. The
container uses its own timezone data. Run ~just build~ once to add it
to an existing image.

The container defaults to UTC if you omit ~timezone~ or launch with
~--empty-workspace~, which bypasses the YAML configuration.

** Skills

The ~publish-project-pdf~ skill supplies the on-demand workflow for
creating or refining polished PDFs from repository documentation. Its
theme is a starter asset: Codex copies and adapts it only when a
project does not already have a theme. The resulting repository owns
its local copy and never imports the skill at build time, so its
documentation remains reproducible outside this sandbox and does not

The [[file:docs/codex-sandbox.pdf][PDF documentation]] for ~codex-sandbox~ was produced using this very

The ~build-silverbullet-wiki~ skill supplies the conventions for
creating and evolving focused SilverBullet knowledge wikis with
Repeater cards integrated beside the knowledge they test. It covers
wiki structure, Markdown conventions, card placement and display,
parser-safe documentation, and validation. Guidance for writing
pedagogically effective card content remains a separate concern.

** Codex CLI

The image installs the standalone Codex package for its build
architecture. The version and both supported Linux archive checksums
are explicit build arguments in ~Containerfile~.

Before updating, open the GitHub release page for
~rust-v$CODEX_VERSION~ in the [[https://github.com/openai/codex/releases][Codex releases]] and review its
~codex-package_SHA256SUMS~ asset. Then, update ~CODEX_VERSION~,
~CODEX_LINUX_AMD64_SHA256~, and ~CODEX_LINUX_ARM64_SHA256~ together.

A build fails before downloading Codex if the checksum selected for
its architecture is still a placeholder or is not a lowercase
64-character SHA-256 value. After the download, the build also fails
unless the archive's computed SHA-256 matches that recorded checksum
exactly.

** Node.js and npm

The build installs a pinned Node.js LTS release from the official Linux
archive, with separate SHA-256 pins for AMD64 and ARM64. Node.js is an explicit
development tool; the standalone Codex CLI does not require it.

The image uses the npm version bundled with that Node.js archive,
keeping the runtime and package manager on the pairing distributed by
the Node.js project.

Project dependencies remain
in each selected project's ~node_modules~ directory. At runtime,
global npm packages install below ~/home/codex/.local~, whose ~bin~
directory is on ~PATH~:

#+begin_src bash
  npm install
  npm install --global npm-check-updates
#+end_src

The npm download cache lives below ~/tmp/codex-npm-cache~ and is
removed with the container. Package downloads may require network
approval, and persistent global installation may require filesystem
approval when Codex runs these commands. Image-managed global packages
remain installed system-wide.

*** Updating Node.js and npm

Review the intended [[https://nodejs.org/en/download][Node.js LTS release]] and its official checksum file:

#+begin_src bash
  NODE_VERSION='<version>'
  curl --fail --show-error --silent --location \
    "https://nodejs.org/dist/v${NODE_VERSION}/SHASUMS256.txt" \
    | rg "node-v${NODE_VERSION}-linux-(x64|arm64)\\.tar\\.xz$"
#+end_src

Update ~NODE_VERSION~, ~NODE_LINUX_AMD64_SHA256~, and
~NODE_LINUX_ARM64_SHA256~ together in ~Containerfile~, then rebuild.
npm updates alongside Node.js through the release archive. Node.js
security updates require an explicit pin update; pulling a newer
Debian base does not update it.

** Browser tests with Playwright

The image includes the Linux libraries and fonts needed for headless
Chromium, Firefox, and WebKit. Each web project supplies its own
~@playwright/test~ dependency, configuration, and tests. From a
project that already declares Playwright:

#+begin_src bash
  cd /workspace/my-web-project
  npm ci
  npx playwright install chromium firefox webkit
  npx playwright test --workers=1
#+end_src

Browsers are cached by default in ~/home/codex/.cache/ms-playwright~
and persist across containers. Run the install command again after
upgrading the project's Playwright version. Run the application
inside the container and use its loopback URL in the test configuration.
Downloads, persistent cache writes, and local browser tests may
require Codex approval.

The root filesystem is read-only: system dependencies are installed
only during the image build. Update ~PLAYWRIGHT_VERSION~ in
~Containerfile~ and rebuild when additional libraries are needed;
do not use ~install-deps~ or ~--with-deps~ at runtime. The launcher
provides 1 GiB of private shared memory for browsers. Save reports and
traces under the mounted project so they persist on the host.

** Python with uv

~uv~ reads a project's ~pyproject.toml~, ~uv.lock~, and
~.python-version~ files and installs a matching Python version when
needed:

#+begin_src bash
  uv sync
  uv run python --version
#+end_src

Python versions and installed tools live below ~/home/codex~, so they
survive container and image replacement. The download cache lives
below ~/tmp/codex-uv-cache~ and is removed with the container. Project
virtual environments remain in their selected working
directories. ~UV_LINK_MODE~ is set to ~copy~ because the cache and
project environments are on different filesystems.

Python and package downloads may require network approval, and
persistent Python or tool installation may require filesystem approval
when Codex runs these commands.

*** Updating uv

The image pins both the uv release and the exact SHA-256 of its
architecture-aware installer. To prepare an update:

#+begin_src bash
  UV_VERSION='<version>'
  uv_releases='https://github.com/astral-sh/uv/releases/download'
  curl --fail --show-error --silent --location \
    "${uv_releases}/${UV_VERSION}/uv-installer.sh" \
    --output /tmp/install-uv.sh
  grep '^APP_VERSION=' /tmp/install-uv.sh
  sha256sum /tmp/install-uv.sh
#+end_src

Update ~UV_VERSION~ and ~UV_INSTALLER_SHA256~ together in
~Containerfile~, review the installer changes, and rebuild the image.

** Repeater

[[https://github.com/shaankhosla/repeater][Repeater]] is installed system-wide from the official prebuilt archive
for the image architecture. It can validate Markdown cards without a
temporary download or a user-global installation:

#+begin_src bash
  repeater --version
  repeater check . --plain
#+end_src

*** Updating Repeater

The image pins the Repeater version and the official SHA-256 digests
for both supported Linux architectures. Obtain the release asset
metadata from GitHub before an update:

#+begin_src bash
  REPEATER_VERSION='<version>'
  curl --fail --show-error --silent --location \
    "https://api.github.com/repos/shaankhosla/repeater/releases/tags/v${REPEATER_VERSION}" \
    | jq -r '.assets[] | select(.name | test("^repeater-(aarch64|x86_64)-unknown-linux-gnu\\.tar\\.xz$")) | [.name, .digest] | @tsv'
#+end_src

Update ~REPEATER_VERSION~, ~REPEATER_LINUX_AMD64_SHA256~, and
~REPEATER_LINUX_ARM64_SHA256~ together in ~Containerfile~, then
rebuild the image.

** Go

The official Go toolchain is installed system-wide at ~/usr/local/go~.
~GOPATH~ is ~/home/codex/go~, and its ~bin~ directory is on ~PATH~, so
tools installed with ~go install~ are immediately available and
survive container replacement:

#+begin_src bash
  go version
  go test ./...
  go install golang.org/x/tools/gopls@latest
#+end_src

Module and build caches live below ~/tmp/codex-go-cache~ and are
removed with the container. Installed tools live below
~/home/codex/go~ in the persistent volume. Project source and vendor
directories remain in the selected working directory. Downloads may
require network approval, and persistent tool installation may require
filesystem approval when Codex runs these commands.

*** Updating Go

The image pins the Go version and the official SHA-256 checksums for
both supported Linux architectures. Obtain the current release
metadata from Go's official download endpoint:

#+begin_src bash
  curl --fail --show-error --silent --location \
    "https://go.dev/dl/?mode=json" \
    | jq '.[0] | {version, files: [.files[] | select(.os == "linux" and (.arch == "amd64" or .arch == "arm64")) | {arch, sha256}]}'
#+end_src

Update ~GO_VERSION~, ~GO_LINUX_AMD64_SHA256~, and
~GO_LINUX_ARM64_SHA256~ together in ~Containerfile~, then rebuild the
image.

** Java with SDKMAN

SDKMAN is seeded for new home volumes and loaded automatically for
Bash commands. Its files and downloaded SDKs live in the persistent
home volume, so installed JDKs survive container and image replacement:

#+begin_src bash
  sdk list java
  sdk install java 21.0.12-tem
  sdk install java 17.0.20-tem
  sdk default java 21.0.12-tem
  java -version
#+end_src

For a project-specific JDK, enter the project directory and create an
SDKMAN environment file:

#+begin_src bash
  sdk env init
#+end_src

Edit ~.sdkmanrc~ to select the desired version, then activate it with
~sdk env~. Listing or downloading SDKs may require network approval
when Codex runs the command.

SDKMAN's automatic startup connectivity check is disabled because
Codex commands do not have network access by default. The entrypoint
enforces this setting for both new and existing home volumes.

*** Updating SDKMAN

The SDKMAN bootstrap URL is mutable. The image therefore pins the
bootstrap script's exact SHA-256 along with the CLI and native
component versions. A changed script fails the build instead of
silently installing different code.

Confirm the intended release on the SDKMAN [[https://github.com/sdkman/sdkman-cli/releases][releases page]], then inspect
and hash the bootstrap script:

#+begin_src bash
  curl --fail --show-error --silent --location \
    "https://get.sdkman.io?rcupdate=false" \
    --output /tmp/install-sdkman.sh
  grep '^export SDKMAN_\(VERSION\|NATIVE_VERSION\)=' /tmp/install-sdkman.sh
  sha256sum /tmp/install-sdkman.sh
#+end_src

Update ~SDKMAN_VERSION~, ~SDKMAN_NATIVE_VERSION~, and
~SDKMAN_INSTALLER_SHA256~ together in ~Containerfile~, review the
script, and rebuild. SDKMAN's published GitHub checksum covers its
release ZIP, not the bootstrap script, so it cannot be used as
~SDKMAN_INSTALLER_SHA256~.

The image seed initializes SDKMAN only when its files are absent from
the persistent home. Rebuilding does not replace an existing SDKMAN
installation or its installed JDKs.

** Ansible authoring and validation

The image includes Ansible Core, ~ansible-lint~, and ~yamllint~ for
authoring and locally validating playbooks, roles, and collections. Useful
commands include:

#+begin_src bash
  ansible-playbook --syntax-check playbook.yml
  ansible-lint
  yamllint .
  ansible-doc ansible.builtin.copy
  ansible-config dump
#+end_src

Ansible's local temporary files are directed to ~/tmp~, which remains writable
inside Codex's sandbox and is removed with the container.

The image-managed Codex instructions prohibit Ansible commands that connect to
or change remote hosts. This includes check mode, which still contacts managed
hosts, and dynamic inventory queries that contact external services. Ansible
is present as an authoring and validation tool, not as authorization to deploy.

Project-specific collections remain declared in each project's
~requirements.yml~ and can be installed with ~ansible-galaxy~ when requested.
Collection downloads may require network approval.

** Lean 4 with Elan

Elan and its ~lean~ and ~lake~ proxies are installed
system-wide. Downloaded Lean toolchains live in the persistent home
volume. Inside a Lean project, ~lean~ and ~lake~ select the version
from ~lean-toolchain~ and download it when necessary:

#+begin_src bash
  lake build
  lean Main.lean
#+end_src

Outside a project with a ~lean-toolchain~ file, select a default
first:

#+begin_src bash
  elan default stable
  lean --version
#+end_src

Toolchain and Lake dependency downloads may require network approval
when Codex runs them.

** Publishing

Pandoc can produce standalone HTML, DOCX, EPUB, and other document
formats directly from Markdown. Typst provides PDF typesetting without
a LaTeX installation. For example:

#+begin_src bash
  pandoc report.md --pdf-engine=typst --output=report.pdf
#+end_src

Typst can also compile ~.typ~ sources directly:

#+begin_src bash
  typst compile report.typ report.pdf
#+end_src

Typst Universe packages are downloaded on demand and cached below
~/home/codex/.cache~ in the persistent home volume. Their first use may
require network approval.
Prefer project-local templates when a build must work offline or use
only repository-reviewed inputs.

*** Updating Typst

The image pins the Typst version and official GitHub release SHA-256
digests for both supported Linux architectures. Query the intended
release metadata before an update:

#+begin_src bash
  TYPST_VERSION='<version>'
  curl --fail --show-error --silent --location \
    "https://api.github.com/repos/typst/typst/releases/tags/v${TYPST_VERSION}" \

the image.

* Isolation boundary

The outer Podman container:

- Runs rootless with ~--userns=keep-id~.

- Drops all Linux capabilities and enables ~no-new-privileges~.

- Uses a read-only root filesystem and a 512-process limit.

- Provides private shared memory for browsers without sharing the
  host's IPC namespace.

- Mounts only explicitly selected host directories, if any, and its
  private home volume.

- Does not mount the host home, SSH configuration, environment, or
  Podman API socket.

- Uses private SELinux relabeling for selected working directories.

Podman's minimal init process runs as PID 1 to forward signals and
reap orphaned children. Within this boundary, Codex uses its normal
~bubblewrap~ and seccomp sandbox with the ~container-workspace~ profile.
The primary project and explicitly added projects form the conversation's
writable scope. Within these roots, the profile keeps ~.git~ read-only
for sandboxed commands.

The bundled rules in ~/etc/codex/rules/git.rules~ preapprove ~git commit~
and ~git switch~. These commands run outside the Codex sandbox, within
the Podman container.

If commands fail with a ~bwrap~ or namespace error, do not disable the
Codex sandbox. The host's rootless Podman configuration must support
unprivileged user namespaces for both isolation layers to work.

** Network boundary

Codex needs network access to communicate with OpenAI, so the outer
container has Podman's normal outbound network access. Sandboxed
commands remain subject to the permission profile's network restrictions
and approval policy. No outer egress allowlist is currently configured.

* Releases

Releases are created manually through the ~Release~ workflow in GitHub
Actions. Run the workflow from ~master~ and choose a ~patch~, ~minor~,
or ~major~ version increment.

The workflow finds the latest stable ~vMAJOR.MINOR.PATCH~ tag, applies
the selected increment, creates the resulting tag at the selected
~master~ commit, and creates a GitHub release with generated notes and
the tracked PDF from that commit. The release asset is named
~codex-sandbox-vMAJOR.MINOR.PATCH.pdf~. If the repository has no
version tags yet, the calculation starts at ~v0.0.0~.

Pushes and pull requests do not trigger releases. The workflow does
not publish packages or container images.
