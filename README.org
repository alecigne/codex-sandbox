#+title: Codex sandbox

A personal development environment for Codex CLI, powered by rootless
Podman.

It keeps the container boundary and Codex's own Linux sandbox enabled:
Podman exposes only explicitly selected working directories, and Codex
runs generated commands through ~bubblewrap~ and seccomp in
~workspace-write~ mode.

This README is also available [[file:docs/codex-sandbox.pdf][as a PDF]].

* AI-assisted development

Development is assisted by Codex CLI under close human direction. Each
new version of ~codex-sandbox~ is developed from within the current
version, so the project also exercises the environment it builds.

* Requirements

- Rootless Podman
- Bash and standard GNU command-line tools
- Unprivileged user namespaces on the host
- ~just~ on the host if you want to use the repository recipes
- ShellCheck on the host if you want to run ~just check~

Tools used inside the sandbox are installed in the image; host
installations are not exposed to the container.

* Usage

** Launch Codex

Pass one or more host working directories to the launcher:

#+begin_src bash
  ~/src/codex-sandbox/run.bash ~/src/my-project
#+end_src

For a shorter command, create a symlink from a directory on the host's
~PATH~:

#+begin_src bash
  ln --symbolic ~/src/codex-sandbox/run.bash ~/bin/sbx
  sbx ~/src/my-project
#+end_src

The image is built automatically the first time. Codex starts in
~/workspace~, with each selected directory mounted below it using its
basename. For example:

#+begin_src bash
  ~/src/codex-sandbox/run.bash ~/src/frontend ~/src/backend
#+end_src

This creates ~/workspace/frontend~ and ~/workspace/backend~; neither
directory is treated as primary. Selected directory basenames must be
unique within a launch.

To launch with an empty, disposable workspace and no host working
directory mounted, use the explicit ~--empty-workspace~ option:

#+begin_src bash
  ~/src/codex-sandbox/run.bash --empty-workspace
#+end_src

The launcher never infers a working directory from the current
directory. Calling it without either ~--empty-workspace~ or at least
one directory is an error. Arguments after ~--~ can also be used in
empty-workspace mode.

Arguments after ~--~ are passed to Codex:

#+begin_src bash
  ~/src/codex-sandbox/run.bash ~/src/my-project -- --model gpt-5.6-sol
#+end_src

Building and launching are separate operations. To build or refresh
the image without launching Codex, run ~--build~ by itself:

#+begin_src bash
  ~/src/codex-sandbox/run.bash --build
#+end_src

** Just recipes

The ~Justfile~ wraps the common repository workflows. Run ~just~ at
any time to list the available recipes.

|---------------------+---------------------------------------------------------------------------|
| Recipe              | Action                                                                    |
|---------------------+---------------------------------------------------------------------------|
| ~check~             | Run Bash syntax checks, ShellCheck, launcher help, and ~git diff --check~ |
| ~configure-signing~ | Configure this clone to sign commits with the owner's GPG key             |
| ~pdf~               | Render this README as a styled PDF through Pandoc and Typst               |
| ~build~             | Build or refresh the image without launching Codex                        |
| ~run ARGS...~       | Forward arguments to ~run.bash~ and launch Codex                          |
| ~containers~        | List running containers created from the sandbox image                    |
| ~shell [CONTAINER]~ | Open a login Bash shell in a running sandbox container                    |
|---------------------+---------------------------------------------------------------------------|

For example:

#+begin_src bash
  just check                         # Run static validation
  just configure-signing             # Configure signed commits in this clone
  just pdf                           # Render docs/codex-sandbox.pdf
  just build                         # Build or refresh without launching
  just run --empty-workspace         # Launch without host workspace mounts
  just run ~/src/my-project          # Launch Codex
  just containers                    # List running sandbox containers
  just shell                         # Open Bash in the running container
#+end_src

Run ~just shell~ from another terminal while Codex is running. If
several sandbox containers are active, select one explicitly:

#+begin_src bash
  just shell CONTAINER_ID_OR_NAME
#+end_src

Arguments to ~just run~ are forwarded to ~run.bash~, including the
separator for Codex arguments:

#+begin_src bash
  just run ~/src/my-project -- --model gpt-5.6-sol
#+end_src

* Releases

Releases are created manually through the ~Release~ workflow in GitHub
Actions. Run the workflow from ~master~ and choose a ~patch~, ~minor~,
or ~major~ version increment.

The workflow finds the latest stable ~vMAJOR.MINOR.PATCH~ tag, applies
the selected increment, creates the resulting tag at the selected
~master~ commit, and creates a GitHub release with generated notes. If
the repository has no version tags yet, the calculation starts at
~v0.0.0~.

Pushes and pull requests do not trigger releases. The workflow does
not upload build artifacts or publish packages or container images.

* Image construction

The image is built from ~node:24-trixie-slim~ and tagged
~codex-sandbox:local~. The ~Containerfile~:

1. Renames the base image's unprivileged UID/GID 1000 account to
   ~codex~.
2. Installs the Debian-packaged system and development tools.
3. Installs the pinned, checksum-verified standalone Codex CLI package.
4. Installs the pinned ast-grep release through npm.
5. Installs uv from a versioned, checksum-verified installer.
6. Installs the checksum-verified official Go toolchain for the image
   architecture.
7. Installs the checksum-verified official Typst CLI for the image
   architecture.
8. Creates a checksum-verified SDKMAN seed for new home volumes.
9. Copies the repository's custom home and entrypoint into the image.
10. Switches permanently to the unprivileged ~codex~ user.

The resulting container root filesystem is read-only at
runtime. Writable locations are mounted explicitly by ~run.bash~.

To build or refresh the image without launching Codex:

#+begin_src bash
  just build
  # or
  ./run.bash --build
#+end_src

Every build uses Podman's ~--pull=newer~ policy. This checks for a
newer ~node:24-trixie-slim~ base so current Node and Debian package
updates are incorporated when available.

* Custom home

The repository's sparse ~home/~ directory is the image-managed portion
of ~/home/codex~.

During the image build, this tree is copied to
~/usr/local/share/codex-sandbox/home~. At every container start, the
entrypoint overlays it onto ~/home/codex~. Matching paths are
refreshed from the image; files absent from the repository template
are left untouched.

This separates two kinds of home data:

- Repository-managed configuration comes from ~home/~ and changes
  through an image rebuild.

- Runtime state such as Codex credentials, sessions, user-installed
  tools, and downloaded toolchains remains in the persistent
  ~codex-sandbox-home~ volume.

Removing a path from ~home/~ does not remove a copy already present in
the persistent volume. Deletion requires an explicit migration or
recreation of the volume.

** Global instructions and skills

The custom home provides a natural place for global Codex instructions
and deliberate personal skills:

#+begin_example
  home/
  ├── .agents/
  │   └── skills/
  │       └── publish-project-pdf/
  │           ├── SKILL.md
  │           ├── agents/openai.yaml
  │           ├── assets/theme.typ
  │           └── references/visual-review.md
  └── .codex/
      └── AGENTS.md
#+end_example

This makes ~codex-sandbox~ not only a development environment, but
also a convenient Git-backed set of instructions for Codex.

The current ~home/.codex/AGENTS.md~ explains the workspace layout and
installed tools to every Codex session and routes polished PDF
requests to the personal skill. Project-level ~AGENTS.md~ files remain
scoped to their own selected directories and take precedence where
they apply.

The ~publish-project-pdf~ skill supplies the on-demand workflow for
creating or refining polished PDFs from repository documentation. Its
theme is a starter asset: Codex copies and adapts it only when a
project does not already have a theme. The resulting repository owns
its local copy and never imports the skill at build time, so its
documentation remains reproducible outside this sandbox and does not
change silently when the image is updated.

The [[file:docs/codex-sandbox.pdf][PDF documentation]] for ~codex-sandbox~ was produced using this very
skill.

** Codex CLI

The image installs the standalone Codex package for its build
architecture. The version and both supported Linux archive checksums
are explicit build arguments in ~Containerfile~.

Before updating, open the GitHub release page for
~rust-v$CODEX_VERSION~ (for example, [[https://github.com/openai/codex/releases/tag/rust-v0.155.1][here]] for v0.155.1) and review its
~codex-package_SHA256SUMS~ asset. Then, update ~CODEX_VERSION~,
~CODEX_LINUX_AMD64_SHA256~, and ~CODEX_LINUX_ARM64_SHA256~ together.

A build fails before downloading Codex if the checksum selected for
its architecture is still a placeholder or is not a lowercase
64-character SHA-256 value. After the download, the build also fails
unless the archive's computed SHA-256 matches that recorded checksum
exactly.

** Node.js and npm

Node.js and npm come from the base image. Project dependencies remain
in each selected project's ~node_modules~ directory. At runtime,
global npm packages install below ~/home/codex/.local~, whose ~bin~
directory is on ~PATH~:

#+begin_src bash
  npm install
  npm install --global npm-check-updates
#+end_src

The npm download cache lives below ~/tmp/codex-npm-cache~ and is
removed with the container. Package downloads may require network
approval, and persistent global installation may require filesystem
approval when Codex runs these commands. Image-managed global packages
remain installed system-wide.

** Python with uv

~uv~ reads a project's ~pyproject.toml~, ~uv.lock~, and
~.python-version~ files and installs a matching Python version when
needed:

#+begin_src bash
  uv sync
  uv run python --version
#+end_src

Python versions and installed tools live below ~/home/codex~, so they
survive container and image replacement. The download cache lives
below ~/tmp/codex-uv-cache~ and is removed with the container. Project
virtual environments remain in their selected working
directories. ~UV_LINK_MODE~ is set to ~copy~ because the cache and
project environments are on different filesystems.

Python and package downloads may require network approval, and
persistent Python or tool installation may require filesystem approval
when Codex runs these commands.

*** Updating uv

The image pins both the uv release and the exact SHA-256 of its
architecture-aware installer. To prepare an update:

#+begin_src bash
  UV_VERSION=0.12.17
  curl --fail --show-error --silent --location \
    "https://astral.sh/uv/${UV_VERSION}/install.sh" \
    --output /tmp/install-uv.sh
  grep '^APP_VERSION=' /tmp/install-uv.sh
  sha256sum /tmp/install-uv.sh
#+end_src

Update ~UV_VERSION~ and ~UV_INSTALLER_SHA256~ together in
~Containerfile~, review the installer changes, and rebuild the image.

** Go

The official Go toolchain is installed system-wide at ~/usr/local/go~.
~GOPATH~ is ~/home/codex/go~, and its ~bin~ directory is on ~PATH~, so
tools installed with ~go install~ are immediately available and
survive container replacement:

#+begin_src bash
  go version
  go test ./...
  go install golang.org/x/tools/gopls@latest
#+end_src

Module and build caches live below ~/tmp/codex-go-cache~ and are
removed with the container. Installed tools live below
~/home/codex/go~ in the persistent volume. Project source and vendor
directories remain in the selected working directory. Downloads may
require network approval, and persistent tool installation may require
filesystem approval when Codex runs these commands.

*** Updating Go

The image pins the Go version and the official SHA-256 checksums for
both supported Linux architectures. Obtain the current release
metadata from Go's official download endpoint:

#+begin_src bash
  curl --fail --show-error --silent --location \
    "https://go.dev/dl/?mode=json" \
    | jq '.[0] | {version, files: [.files[] | select(.os == "linux" and (.arch == "amd64" or .arch == "arm64")) | {arch, sha256}]}'
#+end_src

Update ~GO_VERSION~, ~GO_LINUX_AMD64_SHA256~, and
~GO_LINUX_ARM64_SHA256~ together in ~Containerfile~, then rebuild the
image.

** Java with SDKMAN

SDKMAN is loaded automatically for Bash commands. Its files and
downloaded SDKs live in the persistent home volume, so installed JDKs
survive container and image replacement:

#+begin_src bash
  sdk list java
  sdk install java 21.0.12-tem
  sdk install java 17.0.20-tem
  sdk default java 21.0.12-tem
  java -version
#+end_src

For a project-specific JDK, enter the project directory and create an
SDKMAN environment file:

#+begin_src bash
  sdk env init
#+end_src

Edit ~.sdkmanrc~ to select the desired version, then activate it with
~sdk env~. Listing or downloading SDKs may require network approval
when Codex runs the command.

SDKMAN's automatic startup connectivity check is disabled because
Codex commands do not have network access by default. The entrypoint
enforces this setting for both new and existing home volumes.

*** Updating SDKMAN

The SDKMAN bootstrap URL is mutable. The image therefore pins the
bootstrap script's exact SHA-256 along with the CLI and native
component versions. A changed script fails the build instead of
silently installing different code.

Confirm the intended release on the SDKMAN [[https://github.com/sdkman/sdkman-cli/releases][releases page]], then inspect
and hash the bootstrap script:

#+begin_src bash
  curl --fail --show-error --silent --location \
    "https://get.sdkman.io?rcupdate=false" \
    --output /tmp/install-sdkman.sh
  grep '^export SDKMAN_\(VERSION\|NATIVE_VERSION\)=' /tmp/install-sdkman.sh
  sha256sum /tmp/install-sdkman.sh
#+end_src

Update ~SDKMAN_VERSION~, ~SDKMAN_NATIVE_VERSION~, and
~SDKMAN_INSTALLER_SHA256~ together in ~Containerfile~, review the
script, and rebuild. SDKMAN's published GitHub checksum covers its
release ZIP, not the bootstrap script, so it cannot be used as
~SDKMAN_INSTALLER_SHA256~.

The image seed initializes SDKMAN only when its files are absent from
the persistent home. Rebuilding does not replace an existing SDKMAN
installation or its installed JDKs.

** Lean 4 with Elan

Elan and its ~lean~ and ~lake~ proxies are installed
system-wide. Downloaded Lean toolchains live in the persistent home
volume. Inside a Lean project, ~lean~ and ~lake~ select the version
from ~lean-toolchain~ and download it when necessary:

#+begin_src bash
  lake build
  lean Main.lean
#+end_src

Outside a project with a ~lean-toolchain~ file, select a default
first:

#+begin_src bash
  elan default stable
  lean --version
#+end_src

Toolchain and Lake dependency downloads may require network approval
when Codex runs them.

** Publishing

Pandoc can produce standalone HTML, DOCX, EPUB, and other document
formats directly from Markdown. Typst provides PDF typesetting without
a LaTeX installation. For example:

#+begin_src bash
  pandoc report.md --pdf-engine=typst --output=report.pdf
#+end_src

Typst can also compile ~.typ~ sources directly:

#+begin_src bash
  typst compile report.typ report.pdf
#+end_src

Typst Universe packages are downloaded on demand and cached in the
persistent home volume. Their first use may require network approval.
Prefer project-local templates when a build must work offline or use
only repository-reviewed inputs.

*** Updating Typst

The image pins the Typst version and official GitHub release SHA-256
digests for both supported Linux architectures. Query the intended
release metadata before an update:

#+begin_src bash
  TYPST_VERSION=0.15.1
  curl --fail --show-error --silent --location \
    "https://api.github.com/repos/typst/typst/releases/tags/v${TYPST_VERSION}" \
    | jq -r '.assets[] | select(.name | test("(aarch64|x86_64)-unknown-linux-musl\\.tar\\.xz$")) | [.name, .digest] | @tsv'
#+end_src

Update ~TYPST_VERSION~, ~TYPST_LINUX_AMD64_SHA256~, and
~TYPST_LINUX_ARM64_SHA256~ together in ~Containerfile~, then rebuild
the image.

* Filesystem and persistence

|-------------------------------------+-----------------------------+-----------------------------|
| Location                            | Backing                     | Lifetime                    |
|-------------------------------------+-----------------------------+-----------------------------|
| Selected ~/workspace/NAME~ children | Optional host bind mounts   | Persists on the host        |
| ~/workspace~ root                   | 1 GiB private tmpfs         | Removed with the container  |
| ~/home/codex~                       | ~codex-sandbox-home~ volume | Persists across containers  |
| ~/tmp~                              | 1 GiB private tmpfs         | Removed with the container  |
| ~/run~                              | 64 MiB private tmpfs        | Removed with the container  |
| Container root                      | Read-only image             | Replaced with the container |
|-------------------------------------+-----------------------------+-----------------------------|

Files written directly to ~/workspace~ disappear when the container
exits. Only changes inside selected child directories persist on the
host. In ~--empty-workspace~ mode, no host working directory is
mounted and every file created below ~/workspace~ is disposable.

The home volume contains Codex login and session state, user-global
npm packages, uv-managed Python versions and tools, Go-installed
tools, cached Typst Universe packages, SDKMAN and installed JDKs, and
Elan-managed Lean toolchains. The container itself is launched with
~--rm~; only this volume and selected host directories outlive it.

* Isolation boundary

The outer Podman container:

- Runs rootless with ~--userns=keep-id~.

- Drops all Linux capabilities and enables ~no-new-privileges~.

- Uses a read-only root filesystem and a 512-process limit.

- Mounts only explicitly selected host directories, if any, and its
  private home volume.

- Does not mount the host home, SSH configuration, environment, or
  Podman API socket.

- Uses private SELinux relabeling for selected working directories.

Podman's minimal init process runs as PID 1 to forward signals and
reap orphaned children. Within this boundary, Codex retains its normal
~bubblewrap~/seccomp sandbox with ~workspace-write~ access and
approval on demand.

If commands fail with a ~bwrap~ or namespace error, do not disable the
Codex sandbox. The host's rootless Podman configuration must support
unprivileged user namespaces for both isolation layers to work.

** Network boundary

Codex needs network access to communicate with OpenAI, so the outer
container has Podman's normal outbound network access. Commands
spawned by Codex remain subject to its ~workspace-write~ network
restrictions and approval policy. No outer egress allowlist is
currently configured.

* Remove persistent state

After every sandbox container has stopped, the persistent home can be
removed:

#+begin_src bash
  podman volume rm codex-sandbox-home
#+end_src

This permanently deletes Codex credentials and sessions, user-global
npm packages, uv-managed Python versions and tools, Go-installed
tools, cached Typst Universe packages, SDKMAN and its installed JDKs,
and Elan's downloaded Lean toolchains and configuration. It does not
affect selected host working directories.
